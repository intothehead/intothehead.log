PODECK에서 Unity로 만든 전투를 Next.js 페이지 안에서 실행하면서 다룬 다섯 가지를 정리합니다. 웹과 Unity가 데이터를 주고받는 통로, Unity 인스턴스를 띄우고 내리는 수명주기, 빌드 파일을 브라우저에 제대로 보내는 방법, 전투 결과가 두 번 저장되지 않게 막은 방법, 1GB가 넘던 빌드 용량을 줄인 방법입니다.

## 1. 웹과 Unity 사이의 통로

웹과 Unity는 서로의 함수를 직접 부를 수 없습니다. 그래서 **웹에서 Unity로는 Unity가 제공하는 `SendMessage`를** 쓰고, **Unity에서 웹으로는 브라우저 이벤트(`CustomEvent`)를** 썼습니다.

웹은 전투에 필요한 세션(덱, 층)을 서버에서 받아 JSON 문자열로 Unity에 넘깁니다. `SendMessage`는 Unity 안의 오브젝트 이름과 메서드 이름을 문자열로 지정해 호출합니다.

**웹 → Unity: 세션 JSON 전달**

```ts
unityRef.current?.SendMessage(
  "WebGameSessionReceiver", // Unity 안의 오브젝트 이름
  "ApplySessionJson",       // 그 오브젝트의 메서드 이름
  JSON.stringify(payload),  // 덱·층 정보
);
```

Unity의 C# 코드는 브라우저 자바스크립트를 직접 부를 수 없어서, 작은 JS 플러그인을 거쳐 브라우저에 `podeck:unity-event` 이벤트를 발생시킵니다. **이벤트 이름은 하나로 두고**, 결과·홈으로·다시 하기·다음 층 같은 종류는 `eventName`으로 나눴습니다.

**Unity → 웹: 이벤트로 결과와 요청 보내기**

```csharp
[DllImport("__Internal")]
private static extern void PodeckDispatchUnityEvent(string eventName, string json);

public static bool ReportBattleResult(bool won, int floor, int turnCount, int rewardPackCount)
{
    // …
    return Dispatch("battleResult", json);
}
```

**웹: 이벤트 하나를 받아 종류별로 처리**

```ts
const handleUnityEvent = (event: Event) => {
  const { eventName, json } = (event as CustomEvent<UnityEventDetail>).detail;

  if (eventName === "battleResult") { /* 결과 저장 */ }
  if (eventName === "homeRequested") { /* 결과 저장을 기다린 뒤 홈으로 */ }
  if (eventName === "nextFloorRequested") { /* 다음 층 세션을 받아 다시 전달 */ }
};

window.addEventListener("podeck:unity-event", handleUnityEvent);
```

## 2. Unity 인스턴스 수명주기

Unity WebGL은 수십 MB의 빌드를 내려받고 메모리를 크게 잡는 무거운 프로그램입니다. 그래서 띄울 때와 내릴 때 두 가지를 챙겼습니다.

첫째, Unity를 시작하는 스크립트(loader)는 화면에 들어올 때마다 넣지 않고 **한 번만 받습니다.** 받는 중에 다시 요청되면 같은 약속(Promise)을 기다리고, 실패하면 비워서 다시 받을 수 있게 했습니다.

**loader는 한 번만**

```ts
let unityLoaderPromise: Promise<void> | null = null;

function loadUnityLoader() {
  if (window.createUnityInstance) return Promise.resolve(); // 이미 받았으면 다시 넣지 않음
  if (unityLoaderPromise) return unityLoaderPromise;       // 받는 중이면 같은 약속을 기다림

  unityLoaderPromise = new Promise((resolve, reject) => {
    const script = document.createElement("script");
    script.src = UNITY_LOADER_URL;
    script.onload = () => resolve();
    script.onerror = () => {
      unityLoaderPromise = null; // 실패하면 다시 받을 수 있게
      reject(new Error("Unity loader를 불러오지 못했습니다."));
    };
    document.body.appendChild(script);
  });

  return unityLoaderPromise;
}
```

둘째, Unity 인스턴스 생성은 비동기라 시간이 걸립니다. 로딩 중에 사용자가 화면을 떠나면, 정리 함수가 실행되는 시점에는 **아직 끌 인스턴스가 없습니다.** 그대로 두면 나중에 생성이 끝난 인스턴스가 아무도 모르게 메모리를 차지합니다.

> 그래서 화면을 떠났다는 표시(`disposed`)를 두고, 생성이 끝났을 때 이미 떠났으면 그 자리에서 `Quit()`으로 종료했습니다.

**늦게 생긴 인스턴스까지 종료**

```ts
useEffect(() => {
  let disposed = false;

  async function bootUnity() {
    await loadUnityLoader();
    const unity = await window.createUnityInstance(canvas, config, onProgress);

    if (disposed) {
      await unity.Quit?.(); // 만드는 사이 화면을 떠났으면 바로 종료
      return;
    }
    unityRef.current = unity;
  }

  void bootUnity();

  return () => {
    disposed = true;
    void unityRef.current?.Quit?.(); // 이미 만들어진 인스턴스 종료
    unityRef.current = null;
  };
}, []);
```

## 3. 빌드 파일 전달

Unity 빌드 파일을 브라우저가 올바르게 받아 쓰도록 세 가지를 맞췄습니다.

**gzip 압축 헤더**

Unity 빌드 파일(`.unityweb`)은 gzip으로 압축돼 있습니다. 서버가 **`Content-Encoding: gzip` 헤더로 압축 파일이라고 알려야** 브라우저가 받으면서 풀어 주고, 헤더가 없으면 Unity loader가 파일을 읽지 못합니다. 그래서 `next.config.ts`에서 빌드 파일에 헤더를 붙였습니다.

```ts
async headers() {
  return [
    {
      source: "/unity/Build/:path*.wasm.unityweb",
      headers: [
        { key: "Content-Encoding", value: "gzip" },
        { key: "Content-Type", value: "application/wasm" },
      ],
    },
    // data, framework 파일도 같은 방식
  ];
},
```

**인증 미들웨어 제외**

빌드 파일 요청은 **로그인 확인을 거치지 않고 바로 통과**시켰습니다. 정적 빌드 파일까지 요청마다 세션 확인을 거칠 필요가 없기 때문입니다.

```ts
const publicAssetPrefixes = ["/unity", "/fonts"];

if (publicAssetPrefixes.some((path) => pathname.startsWith(path))) {
  return NextResponse.next(); // 로그인 확인 전에 통과
}
```

**버전 쿼리로 캐시 섞임 막기**

빌드 파일 이름은 빌드마다 같습니다. 그래서 브라우저가 새 data 파일과 옛 wasm 파일처럼 **서로 다른 빌드의 파일을 섞어 쓸 수 있습니다.** 주소에 빌드 버전을 붙여, 빌드가 바뀌면 주소도 바뀌게 했습니다.

```ts
function withUnityBuildVersion(url: string) {
  const separator = url.includes("?") ? "&" : "?";
  return `${url}${separator}v=${encodeURIComponent(UNITY_BUILD_VERSION)}`;
}
// /unity/Build/unity.wasm.unityweb?v=20260623-skill-modal-runtime-moves
```

## 4. 전투 결과 중복 저장 막기

같은 전투 결과가 두 번 저장되면 보상도 두 번 지급됩니다. 그래서 **웹과 서버, 두 겹으로** 막았습니다.

웹에서는 `세션ID:층:승패`를 키로 기록해, 한 페이지 안에서 같은 결과가 다시 오면 무시합니다. 저장이 실패하면 키를 지워 다시 보낼 수 있게 했습니다.

**웹: 결과 키로 같은 결과는 한 번만**

```ts
const key = `${battleSessionId}:${floor}:${won}`;
if (completedResultKeysRef.current.has(key)) return; // 같은 결과는 한 번만
completedResultKeysRef.current.add(key);

completeUnityBattle({ battleSessionId, floor, won, turnCount }).then((result) => {
  if (!result.ok) completedResultKeysRef.current.delete(key); // 실패하면 다시 보낼 수 있게
});
```

웹의 키는 메모리에만 있어서 새로고침하거나 다른 탭에서 보내면 막지 못합니다. 그래서 **서버의 전투 완료 RPC가 최종 방어선**입니다. 세션 행을 `FOR UPDATE`로 잠가 같은 세션의 완료 요청이 동시에 처리되지 않게 하고, 잠근 뒤 완료 여부를 확인해 두 번째 요청을 거절합니다.

**서버: 행을 잠근 뒤 완료 여부 확인**

```sql
select s.completed_at into v_session_completed_at
from public.unity_battle_sessions s
where s.id = p_battle_session_id and s.user_id = v_user_id
for update; -- 같은 세션의 다른 완료 요청은 여기서 기다림

if v_session_completed_at is not null then
  raise exception using errcode = '23505', message = 'battle_session_already_completed';
end if;

update public.unity_battle_sessions set completed_at = now() where id = p_battle_session_id;
```

두 요청이 동시에 오면, 첫 요청이 행을 잠그고 두 번째 요청은 기다립니다. 첫 요청이 완료 시각을 기록하고 끝나면, 두 번째 요청은 그 기록을 보고 거절됩니다.

> 잠금만으로는 중복을 막지 못합니다. 잠금은 순서를 세우고, 실제로 막는 것은 잠근 뒤의 완료 여부 확인입니다.

## 5. 빌드 용량 줄이기

첫 WebGL 빌드는 data 파일이 **약 1,070MB**였습니다. 빌드 리포트를 보니 포켓몬 카드 이미지 809장(장당 약 1.6MB)이 통째로 들어가 있었습니다.

원인은 `Resources` 폴더였습니다. 카드 이미지 DB 에셋이 `Resources`에 있었고, 이 에셋이 이미지 809장을 모두 참조하고 있었습니다. **Unity는 Resources 안의 에셋과 그 에셋이 참조하는 것을 코드에서 쓰든 안 쓰든 전부 빌드에 넣습니다.**

그래서 카드 이미지를 **Supabase Storage로 옮기고**, 웹이 전투 세션에 카드마다 이미지 주소를 실어 보내면 Unity가 **현재 덱에 있는 카드 이미지만 내려받게** 했습니다. 손패가 이미지보다 먼저 뜨지 않도록, 세션을 받자마자 이미지를 미리 받기 시작하고 덱을 만들 때 최대 10초까지 기다립니다.

**웹: 세션의 카드마다 이미지 주소를 붙임**

```ts
cardImageUrl: buildPokemonCardImageUrl("card", input.dexId),
circleImageUrl: buildPokemonCardImageUrl("circle", input.dexId),

function buildPokemonCardImageUrl(kind: "card" | "circle", dexId: number) {
  const paddedDexId = String(dexId).padStart(3, "0");
  return `${supabasePublicUrl}/storage/v1/object/public/pokemon-cards/${kind}/${paddedDexId}.png`;
}
```

이미지를 옮긴 뒤에도 처음 빌드는 그대로 1,070MB였습니다. 이미지 DB 에셋이 아직 `Resources`에 남아 있었기 때문입니다. 이 에셋을 편집기 전용 폴더로 옮긴 뒤에야 data 파일이 **약 1,070MB에서 약 103MB로** 줄었습니다.

> 103MB도 GitHub의 파일 하나당 한도(100MiB)를 넘어서 gzip 압축을 켰고, 그래서 앞에서 본 `Content-Encoding` 헤더가 필요해졌습니다.

## 정리

> 웹과 Unity는 `SendMessage`와 `CustomEvent`로 주고받고, 비동기로 늦게 생기는 Unity 인스턴스는 생성이 끝난 시점에 화면을 떠났는지 다시 확인해 종료합니다. 빌드 파일은 압축 헤더와 버전 주소로 브라우저가 올바른 파일을 받게 하고, 전투 결과는 웹의 결과 키와 서버의 행 잠금·완료 확인으로 한 번만 저장합니다. 빌드 용량은 카드 이미지를 빌드에서 빼 Supabase Storage에서 필요한 것만 받게 해 약 1,070MB에서 약 103MB로 줄였습니다.
