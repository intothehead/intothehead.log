이 블로그는 혼자 만들고 있어서 브랜치를 따로 나누지 않고 한 브랜치에 작은 커밋을 쌓고 있습니다. 하지만 여러 사람이 같은 저장소에서 일하면 같은 방식이 금방 문제가 됩니다. 이 글에서는 혼자 할 때와 팀으로 할 때 브랜치를 나누는 방식을 비교해 봅니다.

## 1. 혼자 할 때: 한 브랜치와 작은 커밋

혼자 작업할 때는 다른 사람과 코드가 부딪힐 일이 없어서 기본 브랜치 하나로도 충분합니다. 대신 커밋을 작게 나누고, 메시지에 무엇을 했는지 분명히 적습니다. 문제가 생겼을 때 어느 커밋에서 시작됐는지 찾기 쉽고, 그 커밋만 되돌리기도 쉽기 때문입니다.

```bash
git add app/posts
git commit -m "글 상세에 썸네일 보여 주기"
git log --oneline
```

이 블로그도 화면 하나를 여러 걸음으로 나눠 걸음마다 커밋했습니다. `git log --oneline`만 봐도 어떤 순서로 만들었는지 다시 따라갈 수 있습니다.

## 2. 팀으로 할 때: 기능마다 브랜치와 Pull Request

여러 사람이 한 브랜치에 바로 커밋하면 서로의 작업이 섞이고, 덜 끝난 기능이 그대로 배포될 수 있습니다. 그래서 기능마다 브랜치를 새로 만들고, 다 끝나면 Pull Request로 리뷰를 받은 뒤 기본 브랜치에 합칩니다. 이 흐름을 GitHub Flow라고 부릅니다.

```bash
git switch -c feature/post-detail
git add .
git commit -m "글 상세 페이지 뼈대 만들기"
git push -u origin feature/post-detail
```

브랜치 이름 앞에 `feature/`, `fix/`처럼 종류를 붙이면 목록만 봐도 무슨 작업인지 알 수 있습니다. 리뷰를 받는 동안 다른 사람은 기본 브랜치에서 계속 일할 수 있고, 문제가 있는 코드는 합치기 전에 걸러집니다.

## 3. 기본 브랜치가 앞서 갔을 때: merge와 rebase

내가 작업하는 동안 다른 사람의 변경이 기본 브랜치에 먼저 합쳐지면, 내 브랜치를 최신 상태로 맞춰야 합니다. 방법은 두 가지입니다.

```bash
git fetch origin

# merge: 합친 기록이 커밋 하나로 남는다
git merge origin/main

# rebase: 내 커밋들을 최신 main 위로 옮겨 다시 쌓는다
git rebase origin/main
git push --force-with-lease
```

`merge`는 기존 기록을 그대로 두어 안전하지만, 합친 흔적이 쌓여 기록이 복잡해집니다. `rebase`는 기록이 한 줄로 깔끔해지지만 커밋을 새로 만들기 때문에 push할 때 원격 기록을 덮어써야 합니다. 그래서 rebase는 나 혼자 쓰는 브랜치에서만 하고, 여러 사람이 같이 쓰는 브랜치에서는 하지 않습니다.

## 4. 배포 일정이 있는 팀: Git Flow

정해진 날에 버전을 내보내는 팀은 Git Flow처럼 브랜치를 더 나누기도 합니다. 개발 중인 코드를 모으는 `develop`, 배포를 준비하는 `release`, 운영 중 급한 수정을 위한 `hotfix` 브랜치를 따로 둡니다. 규칙이 많은 만큼 자주 배포하는 작은 팀에는 오히려 무거울 수 있습니다.

> 브랜치 전략은 팀의 크기와 배포 방식에 맞춰 고르는 것이지, 정답이 하나인 것은 아닙니다.
