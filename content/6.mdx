이 블로그는 혼자 만들고 있어서 브랜치를 따로 나누지 않고 한 브랜치에 작은 커밋을 쌓고 있습니다. 하지만 팀으로 일할 때는 같은 방식이 금방 문제가 됩니다. 이 글에서는 혼자 할 때와 팀으로 할 때 브랜치를 나누는 방식을 비교해 봅니다.

## 1. 혼자 할 때: 한 브랜치와 작은 커밋

혼자 작업할 때는 다른 사람과 코드가 부딪힐 일이 없어서 기본 브랜치 하나로도 충분합니다. 대신 커밋을 작게 나누고, 메시지에 무엇을 했는지 분명히 적습니다. 문제가 생겼을 때 어느 커밋에서 시작됐는지 찾기 쉽기 때문입니다.

```bash
git add app/posts
git commit -m "글 상세에 썸네일 보여 주기"
```

## 2. 팀으로 할 때: 기능마다 브랜치

여러 사람이 한 브랜치에 바로 커밋하면 서로의 작업이 섞이고, 덜 끝난 기능이 그대로 배포될 수 있습니다. 그래서 기능마다 브랜치를 새로 만들고, 다 끝나면 Pull Request로 리뷰를 받은 뒤 기본 브랜치에 합칩니다. 이 흐름을 GitHub Flow라고 부릅니다.

```bash
git switch -c feature/post-detail
git push -u origin feature/post-detail
```

## 3. 배포 일정이 있는 팀: Git Flow

정해진 날에 버전을 내보내는 팀은 Git Flow처럼 브랜치를 더 나누기도 합니다. 개발 중인 코드를 모으는 `develop`, 배포를 준비하는 `release`, 급한 수정을 위한 `hotfix` 브랜치를 따로 둡니다. 규칙이 많은 만큼 작은 팀에는 오히려 무거울 수 있습니다.

> 브랜치 전략은 팀의 크기와 배포 방식에 맞춰 고르는 것이지, 정답이 하나인 것은 아닙니다.
