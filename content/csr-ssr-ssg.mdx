면접에서 "CSR과 SSR의 차이가 무엇인가요?"라는 질문을 받으면, 결국 **화면의 HTML을 언제, 어디서 만드느냐**를 설명하면 됩니다. 이 글에서는 세 가지 방식을 비교하고, Next.js에서는 그 선택이 어떻게 정해지는지 정리합니다.

## 1. CSR: 브라우저가 그린다

CSR(Client-Side Rendering)에서는 서버가 거의 빈 HTML과 자바스크립트 묶음을 보냅니다. 브라우저가 자바스크립트를 내려받아 실행하고, 데이터를 가져온 뒤에야 화면을 그립니다.

```html
<body>
  <div id="root"></div>  <!-- 처음 받은 HTML은 비어 있다 -->
  <script src="/bundle.js"></script>
</body>
```

한 번 불러온 뒤에는 화면 전환이 빠르고 서버 부담이 적습니다. 대신 첫 화면이 늦게 뜨고, 검색 엔진이 빈 HTML만 보고 내용을 읽지 못할 수 있습니다.

## 2. SSR: 요청마다 서버가 그린다

SSR(Server-Side Rendering)에서는 요청이 올 때마다 서버가 데이터를 가져와 완성된 HTML을 만들어 보냅니다. 사용자는 내용이 채워진 화면을 바로 보고, 검색 엔진도 내용을 읽을 수 있습니다.

다만 HTML만으로는 버튼이 동작하지 않습니다. 브라우저가 자바스크립트를 받아 이미 그려진 HTML에 이벤트를 연결하는데, 이 과정을 하이드레이션이라고 합니다. 그리고 요청마다 서버가 계산해야 해서, 서버가 느리면 첫 응답도 늦어집니다.

## 3. SSG: 빌드할 때 미리 그려 둔다

SSG(Static Site Generation)에서는 빌드할 때 HTML을 미리 만들어 두고, 요청이 오면 만들어 둔 파일을 그대로 줍니다. 계산이 없어서 가장 빠르고, 전 세계에 흩어진 CDN에 올려 두기도 좋습니다.

대신 데이터가 바뀌면 다시 빌드해야 합니다. 그래서 블로그 글이나 회사 소개처럼 자주 바뀌지 않는 화면에 어울립니다. 정해진 시간이 지나면 백그라운드에서 다시 만들어 두는 ISR(Incremental Static Regeneration)이라는 중간 방식도 있습니다.

## 4. Next.js에서는 데이터가 방식을 정한다

Next.js App Router에서는 페이지마다 방식을 직접 고르기보다, 그 페이지가 **어떤 데이터를 쓰는지**에 따라 정해집니다. 요청과 상관없는 데이터만 쓰면 빌드할 때 미리 만들어 둡니다. 이 블로그의 글 목록처럼 파일에서 읽는 데이터가 그렇습니다.

```tsx
export default async function AllPosts() {
  const posts = await getPosts(); // 누가 와도 같은 데이터 → 미리 만든다
  return <FilteredPostList posts={posts} />;
}
```

반대로 쿠키처럼 요청마다 달라지는 정보를 읽으면 요청이 올 때 만듭니다.

```tsx
import { cookies } from "next/headers";

async function Greeting() {
  const name = (await cookies()).get("name")?.value; // 사람마다 다른 데이터
  return <p>{name}님, 안녕하세요</p>;
}
```

Cache Components를 켠 Next.js 16에서는 이런 컴포넌트를 `Suspense`로 감쌉니다. 그러면 페이지의 나머지는 미리 만들어 두고, 이 자리만 요청 때 채워서 보냅니다. 한 페이지 안에서 SSG와 SSR을 섞는 셈입니다.

> 어디서 그릴지는 "이 데이터가 누구에게나 같은가?"를 먼저 물어보면 정해집니다.
