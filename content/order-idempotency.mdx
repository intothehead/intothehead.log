## 1. 멱등성과 Idempotency-Key

**멱등성**은 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질을 뜻합니다.

`Idempotency-Key`는 "이 요청은 아까 그 시도와 같은 요청"임을 서버에게 알려 주는 키입니다.

**주문 생성 요청에 키를 붙임**

```ts
export function createOrder(body: OrderRequest, idempotencyKey: string) {
  return apiRequest<OrderCreated>("/api/v1/orders", {
    auth: true,
    method: "POST",
    body,
    headers: { "Idempotency-Key": idempotencyKey },
  });
}
```

## 2. 응답별 키 처리

서버가 주문 내용을 검사하고 거절한 4xx(400 `INVALID_INPUT`, 404 `NOT_FOUND`, 409 `INSUFFICIENT_STOCK`, 쿠폰 오류)는 이 키로 만든 주문이 존재하지 않는다는 뜻이므로, **키를 버리고 거절 사유를 안내**합니다.

**거절이 확정된 4xx는 키를 버림**

```ts
// 서버가 거절을 확정한 4xx만 시도를 버린다.
if (
  error instanceof ApiError &&
  error.status >= 400 &&
  error.status < 500 &&
  !unconfirmedStatuses.has(error.status)
) {
  storage.removeItem(storageKey); // 키를 버림
  throw new OrderRejectedError(error.code); // 거절 사유 안내
}
```

409 `CONFLICT`는 같은 키 요청이 아직 처리 중이라는 뜻이므로 **키를 유지**합니다.

**CONFLICT는 키를 지우지 않음**

```ts
if (error instanceof ApiError && error.code === "CONFLICT")
  throw new OrderAttemptError("같은 주문을 처리하고 있습니다. 잠시 후 다시 시도해주세요.");
```

401, 403은 로그인·권한 단계에서, 408, 429는 시간 초과·요청 제한으로 막힌 응답이라 이전 요청이 주문을 만들었는지 알려 주지 않습니다. FE가 결과를 확정할 수 없으므로 **키를 유지**합니다.

**결과를 확정할 수 없는 상태 번호**

```ts
// 인증·권한·시간 초과·요청 제한 응답만으로는 이전 요청의 생성 여부를 확정할 수 없다.
const unconfirmedStatuses = new Set([401, 403, 408, 429]);
```

5xx와 네트워크 오류는 서버가 주문을 만든 뒤 응답만 사라졌을 수 있어 결과를 알 수 없으므로 **키를 유지**합니다.

**요청 전에 키를 저장하고, 결과를 모르면 지우지 않음**

```ts
// 요청 전에 키를 남겨야 응답 유실·새로고침 뒤에도 같은 키로 서버 결과를 되찾는다.
storage.setItem(storageKey, JSON.stringify(attempt));
try {
  order = await createOrder(attempt.body, attempt.key);
} catch (error) {
  // …
  // 네트워크·5xx·파싱 실패는 키를 지우지 않고 같은 키로 다시 보낸다.
  throw new OrderAttemptError(
    "주문 결과를 확인하지 못했습니다. 다시 시도하면 같은 주문으로 이어집니다.",
  );
}
```

> 판단할 때는 상태 번호만이 아니라 오류 코드도 함께 봅니다. 같은 409라도 `INSUFFICIENT_STOCK`은 버리고 `CONFLICT`는 유지합니다.

**오류 코드를 먼저 보고, 그다음 상태 번호를 봄**

```ts
} catch (error) {
  // 1. 오류 코드가 CONFLICT면 409라도 키를 유지
  if (error instanceof ApiError && error.code === "CONFLICT")
    throw new OrderAttemptError("같은 주문을 처리하고 있습니다. 잠시 후 다시 시도해주세요.");
  // 2. 그 밖의 확정 거절 4xx(409 INSUFFICIENT_STOCK 포함)는 키를 버림
  if (
    error instanceof ApiError &&
    error.status >= 400 &&
    error.status < 500 &&
    !unconfirmedStatuses.has(error.status)
  ) {
    storage.removeItem(storageKey);
    throw new OrderRejectedError(error.code);
  }
  // 3. 나머지는 키를 유지
  throw new OrderAttemptError(
    "주문 결과를 확인하지 못했습니다. 다시 시도하면 같은 주문으로 이어집니다.",
  );
}
```

## 3. 오류 코드별 의미와 처리

**400 INVALID_INPUT: 요청 내용이 잘못됨**

- HTTP 뜻: Bad Request. 요청의 형식이나 값이 규칙에 맞지 않습니다.
- 주문에서: 보낸 주문 내용을 서버가 검사해서 받아들일 수 없다고 판단한 경우입니다. 어떤 값이 어떻게 틀렸을 때 나는지는 BE 코드를 직접 확인하지 않았습니다.
- FE 안내: "주문 내용을 확인하지 못해 주문하지 못했습니다. 리워드와 쿠폰을 확인한 뒤 다시 시도해주세요."
- 키: 버림

```ts
function rejectedOrderMessage(code: string) {
  switch (code) {
    // …
    default: // INVALID_INPUT 등
      return "주문 내용을 확인하지 못해 주문하지 못했습니다. 리워드와 쿠폰을 확인한 뒤 다시 시도해주세요.";
  }
}
```

**404 NOT_FOUND: 주문하려는 대상이 없음**

- HTTP 뜻: Not Found. 요청한 대상을 찾을 수 없습니다.
- 주문에서: 주문하려는 리워드나 옵션이 없는 경우입니다. 삭제됐거나 잘못된 ID일 수 있습니다.
- FE 안내: "주문할 수 없는 리워드나 옵션이 있어 주문하지 못했습니다. 프로젝트에서 리워드를 다시 선택해주세요."
- 키: 버림

```ts
case "NOT_FOUND":
  return "주문할 수 없는 리워드나 옵션이 있어 주문하지 못했습니다. 프로젝트에서 리워드를 다시 선택해주세요.";
```

**409 INSUFFICIENT_STOCK: 재고 부족**

- HTTP 뜻: Conflict. 요청이 서버의 현재 상태와 충돌합니다.
- 주문에서: 고른 리워드의 남은 수량이 주문 수량보다 적은 경우입니다. 예를 들어 다른 사람이 먼저 사서 수량이 줄었을 때입니다.
- FE 안내: "남은 수량이 부족한 리워드가 있어 주문하지 못했습니다. 수량을 확인해주세요." 그리고 리워드 정보를 다시 불러옵니다.
- 키: 버림

```ts
case "INSUFFICIENT_STOCK":
  return "남은 수량이 부족한 리워드가 있어 주문하지 못했습니다. 수량을 확인해주세요.";

// 화면: 쿠폰 오류가 아니면 리워드 정보를 다시 불러온다
if (error instanceof OrderRejectedError) {
  if (error.code.startsWith("COUPON_") && nextCouponCodes.length > 0) void preview.refetch();
  else void rewards.refetch();
}
```

**409 CONFLICT: 같은 키 요청과 충돌**

- HTTP 뜻: 위와 같은 Conflict입니다.
- 주문에서: 멱등 키 관련 충돌로, 두 경우가 있습니다.
  - 같은 키로 보낸 요청이 아직 처리 중일 때(예: 첫 요청이 끝나기 전에 같은 키로 또 보냄)
  - 같은 키에 다른 주문 내용을 보냈을 때
- FE 안내: "같은 주문을 처리하고 있습니다. 잠시 후 다시 시도해주세요."
- 키: 유지. 처리 중이던 요청이 주문을 만들고 있을 수 있기 때문입니다. FE는 항상 저장해 둔 원래 본문을 보내므로, 정상 흐름에서는 두 번째 경우가 생기지 않습니다.

```ts
// 결과를 모르는 시도는 새 주문보다 먼저 같은 키·같은 본문으로 다시 보낸다.
const order = saved.order ?? (await send(storage, storageKey, saved as Attempt));
```

## 4. 함께 알아 둘 쿠폰 오류 (422)

422(Unprocessable Content)는 형식은 맞지만 처리할 수 없다는 뜻입니다. 이것도 확정 거절이라 **키를 버립니다.**

- `COUPON_BUDGET_EXCEEDED`: 쿠폰 예산이 소진됨 → "쿠폰이 모두 소진되어 주문하지 못했습니다."
- `COUPON_NOT_APPLICABLE`: 이 주문에 쓸 수 없는 쿠폰 → "적용할 수 없는 쿠폰이 있어 주문하지 못했습니다."

두 경우 모두 쿠폰을 다시 고르도록 안내하고, 주문 미리보기를 다시 불러옵니다. 코드에는 `COUPON_EXHAUSTED`도 같은 안내로 처리돼 있지만, 이 코드의 상태 번호는 문서에서 확인하지 못했습니다.

```ts
case "COUPON_BUDGET_EXCEEDED":
case "COUPON_EXHAUSTED":
  return "쿠폰이 모두 소진되어 주문하지 못했습니다. 쿠폰을 다시 선택해주세요.";
case "COUPON_NOT_APPLICABLE":
  return "적용할 수 없는 쿠폰이 있어 주문하지 못했습니다. 쿠폰을 다시 선택해주세요.";

// 화면: 쿠폰 오류면 주문 미리보기를 다시 불러온다
if (error.code.startsWith("COUPON_") && nextCouponCodes.length > 0) void preview.refetch();
```

## 정리

> 같은 주문 시도는 같은 `Idempotency-Key`로 보냅니다. 서버가 거절을 확정한 4xx(400 `INVALID_INPUT`, 404 `NOT_FOUND`, 409 `INSUFFICIENT_STOCK`, 422 쿠폰 오류)는 키를 버리고 거절 사유를 안내하고, 409 `CONFLICT`와 401·403·408·429, 5xx·네트워크 오류처럼 주문이 만들어졌는지 알 수 없는 응답은 키를 유지합니다. 판단할 때는 상태 번호와 오류 코드를 함께 봅니다.
